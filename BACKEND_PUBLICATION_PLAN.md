# Backend publication plan

## Release decision

**The private shopping preview works. Public text search needs a reviewed catalogue slice and a verified production API.** Start with a clearly labelled pilot for the brands and categories we can support. A shopper should be able to search without an account, compare the same qualifying sizes and prices, see when each offer was checked, and open the correct merchant product page.

## Implementation sequence

| Order and owner | Work | Evidence required to close the step |
| --- | --- | --- |
| **1. Catalogue and permissions** | Begin with the six styles already carrying reviewed offers. Record the evidence for permitted metadata, description, link, display image and embedding uses independently. Pick eligible fields, brand/department scope and publishable product IDs. Expand the set until shoppers have meaningful choices for the release queries. | A dated manifest lists every proposed style, allowed fields, source, reason, reviewer and revision. Any private or unapproved fields are absent from the public response and public assets. Document what the pilot covers. |
| **2. Data and search** | Refresh the selected variants. Preserve independent size, garment colour, price in paise, check time, stock, preorder and fulfilment. Check URLs and variant landing behaviour. Export current sections and offers for the same revision. Keep older observations visible as last seen. Capture a useful assortment of price points and sizes. | For every pilot style, reconcile source ID and variant ID. Check JNORSS Metallica L, unavailable Thorn Vein XL and Bonkers Signature M. At the latest integration these had ₹1,499, unavailable, and ₹1,799 respectively. Recheck prices and stock at release time. Failing or missing evidence cannot satisfy a strict request. |
| **3. API and deployment** | Package a production-only API. Configure its Supabase URL and server-only credential in the deployment environment, set the port/interface and HTTPS routing for `/api`, keep secrets out of the frontend build, and implement distinct liveness/readiness responses. Review least privilege and the two serving paths. | On a private staging host, a reviewed fixture is searchable and comparable. Missing credentials, an empty catalogue and a database outage each produce an intelligible failure state. The private preview and synthetic products cannot be selected in production. Check the deployed browser origin through to the API. |
| **4. Release and access review** | Verify publication enforcement end to end, including direct database reads with the publishable key, older views/RPCs, the server-only projection, gallery URLs, static brand photos and response caches. The current projection depends on the product publication flag for metadata. Define how a permission withdrawal removes every affected field. | Tests using anonymous and signed-in client privileges show only the intended rows/columns. A revoked product and image disappear within a measured, documented interval. Compare public results with the release manifest. |
| **5. Marketplace quality** | Run the same revision through hosted and private search. Reconcile differences in internal versus merchant IDs, audience extraction, fit, garment colour, print and material evidence. Test all filters enabled for the pilot, exact variants, comparison, pagination and merchant links. Have two shoppers grade the planned 30-query set, including ten held-out queries. | Zero hard-filter violations. For at least 80% of judged queries with three eligible relevant styles, at least three of the top five are relevant. Include genuine zero-result cases. Verify cold and warm latency and p95 load at the declared pilot size. Record every failing case and fix or narrow the advertised scope. |
| **6. Operations and recovery** | Establish permitted offer refreshes with shared domain limits, retry cursors and monitoring. Monitor fresh/last-seen share, stale data, API failures, latency, storage and egress. Complete the deferred private backup and isolated restore before the production cutover. Test reverting a catalogue revision independently of the application revision. | Demonstrate a missed check, a rate-limited source, a database interruption, a successful recovery and a restored backup. Confirm dated browsing continues when stock freshness expires. Set thresholds for the actual free host and agreed pilot load. |
| **7. Controlled publication** | Merge reviewed application and migration changes into the chosen release branch. Rehearse with a private dataset or isolated fixture, sign off the manifest, then release that exact approved subset and check it from the public endpoint. | Published row counts match the signed-off list. Search, compare, click-through, monitoring, cache invalidation and rollback all work on the released revision. Expand by brand/category using the same checklist. |

**First work package after approval.** Catalogue review starts Step 1 with the six candidates. Backend work can prepare Step 3 and production-path tests in parallel. The first joint check uses a JNORSS hoodie with a specific eligible size, the checked item price, unknown fulfilment and the merchant link. A second check must reject the unavailable size. This gives both teams a small, reproducible target before expanding coverage.

## Features with later release dates

- **Photo search** needs licensed or otherwise permitted images for indexing, explicit variant links, evaluation on real garment queries, upload privacy and limits, and staging load tests. The local CPU pilot can continue while text search moves toward release.
- **Weekly price headlines** need two real consecutive accepted snapshots with compatible scope, adequate paired-variant coverage and the documented sample thresholds. Continue collecting eligible history as soon as possible.
- **Delivered price, returns and ready-to-ship filters** need applicable reviewed shipping/return rules and fresh offer/fulfilment evidence. Keep item-price and last-seen browsing available wherever supported.
- **Broader nine-brand coverage** needs further offer and section verification. A release claim covering all nine brands needs representative, usable inventory across them and a dated coverage report.
- **Affiliate revenue** needs merchant/network approval and a tested attribution link for each participating programme. Ordinary merchant click-through can launch first.
